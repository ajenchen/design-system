**目標**:Claude Code、Codex 與未來 provider 共用同一批 canonical bytes、applicable rule coverage、證據要求與 blocking outcome;provider 差異只出現在生成式 discovery/transport adapter。

- **Bootstrap**:`AGENTS.md` 是跨 provider 的簡潔導航;`CLAUDE.md` 是 `@AGENTS.md` + Claude-specific generated-adapter 說明。Nested package instructions 由 `scripts/package-role-sources/` 獨立短 source 生成,root→cwd 累積不得超過 Codex 預設 32KiB。
- **Canonical authority**:`infra/governance/protected-root-classification.json` 封閉 owner/output/non-authority;`packages/governance/canonical/manifest.json` 封閉發布輸入;`scripts/governance-build-graph.json` 只從 canonical source 產生 Claude/Codex/template/fork/control-plane views。Standard release machine SSOT=`infra/governance/release-workflow.json`;`governance/planning/2026-07-16-provider-neutral-governance.md` 為歷史紀錄。
- **Enforcement**:唯一五步=`pr-checks→merge→publish→readback→consumer`;**合併前有一道發版同意閘**(SSOT = AGENTS.md「# Git / release canonical」1.5),其餘全 AUTO;只有未決產品/UI/UX SSOT 真取捨 ASK。Login/MFA/OAuth/credential reference 完成後 AUTO resume。hard gates 清單以 `infra/governance/release-workflow.json` 為準(prose 對照 = `feedback_solo_dev_workflow.md`「Release hard gate」,不在此重述)。
- **Model neutrality**:model judgment 由 content-addressed bounded shards + closed reducer 供給 provider adapter;model 不直接讀 repo,不信任 provider transcript 作為 coverage authority。新 provider 透過 registry/profile/schema/fixture/certification 接軌,未認證即 fail closed。
- **Distribution**:Claude plugin、Codex plugin/hooks、npm package 與 product template 都是不可變 release 的 adapter/delivery view;`ajenchen/workspace` 是下游 product-consumer canary,用來回饋 DS/template/governance/package 的 root cause,不是第二個治理 owner。
- **產品 canary 身分(每 session 必知)+ 操作檔案**:**產品 canary = `ajenchen/workspace`**(2026-11-25 換上;user 原話:「此外，設計系統 repo 要把 canary 換成 ajenchen/workspace，換過來之後，設計系統出新版時，這個 repo 也會自動收到升級 PR。」)。它是由 `ds-product-template` 生出的真實產品 repo(讀回:private、預設分支 main、`template_repository = ajenchen/ds-product-template`、package.json name `ds-product-template`),user 另一個 session 在那裡做產品;在 fleet 語意裡它是唯一登記的 product-consumer(`infra/governance/inventory/managed-repos.json`,血統 `new-snapshot-v2`,`certificationCanaries.product-consumer` 指向它)。**發版時怎麼對它**:`infra/governance/release-workflow.json` 標 `upgrade: automatic`、`delivery: repository-dispatch-pr`、`merge: consumer-owned` —— 第五步自動替它派工(`design-system-published`)、分支出現後開升級 PR、讀回 PR 連結與必過檢查;**不合併、不等合併,它的檢查紅也不讓發版失敗,不是第五步的完成條件**(「只開 PR、不等合併」是 AI 的工程判斷,依據 AGENTS.md「Decision／Engineering Authority」preview-canary 不得進 blocking graph;判定 `scripts/lib/release-consumer-selection.mjs` 的 `consumerBlocksRelease`)。合併那顆 PR 是 workspace 那邊的事,**不得為了讓稽核變綠而替它合併**(dim 64/66 把它記成 `consumerOwned`)。**它那邊要具備的東西**:接收升級的 workflow(聽 `repository_dispatch` 的 `design-system-published`、跑 exact-version `sync-all`、把分支 `automation/design-system-<version>` 推上來)—— 2026-11-25 讀回時**還沒有**(只有 `audit.yml`),在它補上之前第五步只會回報「升級 PR 還沒開出」。必過檢查已具備:ruleset `main-protection` 要求 `Verify consumer`(GitHub Actions)。**登記狀態**:走 `consumerctl plan-registration` 的受審提案(proposalDigest `59e26f7b…`),release-rings 的 onboarding manual blocker 保留、`candidateRelease` 為 null(兩次候選之間);之後要走 `plan-control-plane-update` 時,先照前例 #68 / #81 / #165 把候選推到目標版。**work-management 已退場**(2026-11-25 user 原話:「work-management 那個 repo不要了可以刪掉了」):清冊、release-rings、發版設定都已移除;同一把憑證讀它全部回 404。它的戰役史在 `governance/archive/memory-retired/2026-08-18-prune/`。
