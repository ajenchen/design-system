# 多代理批次:先驗證再放大(2026-11-18 起因,2026-11-21 寫進 repo)

**本檔只放原則與指標**。多包 / 多步工作怎麼實作、怎麼審查、審查幾輪、什麼時候再修,只照 `packages/design-system/ds-canonical/rules/work-process.md`(本檔不重述)。並行上限、負載門檻這類數值不寫在這裡,由當批的工作狀態檔設定(2026-11 那一批:見交接 state/schedule.json 的 settings)。

**Why**(user 2026-11-18 21:17:45 原話,台灣時間):「你這邊應該是否優先完成所有跟避免浪費資源同時確保產出品質完美的相關任務？這樣到時候接手的帳號就不會跟你一樣白痴亂揮霍了？ 然後接著才看你這邊能做多少算多少？ 同時確保不管是任何 session 接手都不會遺漏或中斷任何任務或是去脈絡化解讀該讀的訊息，確保所有任務都能夠被完美收尾」。同日 14:35:05 先問過:「確定所有時間都花得有意義？最有效率同時確保品質完美？」

## 1. 先用小樣本兩面實跑,再放大

- 新的量具、派工設定、合回做法,先在一兩包(或一份小樣本)上實跑,而且兩面都跑:該紅的情況真的紅、該綠的情況真的綠,確認量的是要保證的那件事,才套到整批。
- 量不到 = 量具失效,不是通過;本機量的要是 CI 要的那一份。
- 錨例(2026-11-18):本機檢查少了 CI 的幾步,本機全綠時 PR 必過檢查其實已經紅;有一支量具拿自己跟自己比,永遠綠;完成判定沒等檢查跑完就判通過 —— 都是沒先在小樣本上兩面實跑就放大到整批。

## 2. 整串檢查有全機上限

- 同時跑的整串檢查(合回檢查、裝相依、建置、掃大檔)有全機上限;機器忙過門檻就不開新的,排隊等號。
- 超過上限時的逾時紅是負載造成的假紅,不是產品紅;負載高也不是沒實跑卻判通過的理由。
- 錨例(2026-11-18):同時開了十多個代理、機器滿載,逾時假紅都出在並行最多的時段;負載下測試逾時留下垃圾檔 → 刪檔被擋 → 整包停在未提交。

## 3. 修補不收斂就停下找根因

- 同一包修過還驗出必修,或同一類問題第二次出現 → 停下找根因、改設計,不再修表面(審查與再修的條件照 `rules/work-process.md`)。
- 錨例(2026-11-18 → 11-19):從散文猜相依方向的工具修了好幾輪仍有必修,根因是用正規表示式猜方向,改成結構化的相依清單才收斂;流程藍圖第二版再驗仍有大量必修 → 停下找根因(想把所有紀律做成一整套新記帳平台),收斂成最小可行版。
